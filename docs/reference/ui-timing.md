# UI 美观度与易用性的时点

> **状态：调度建议，不是决策**（2026-09-21）。本文不进入 `decisions.md` 的 D 编号体系，与决策台账冲突时**以台账为准**；也不是 `facts.md` 的证据条目（那是实测/源码/文档的证据台账）。
> **由来**：项目所有者问"界面美观度和易用性是当前阶段的目标吗"，结论是"不是当前阶段目标"；随后要求确定它**落在哪个阶段最合理**，并同意把该结论记录在此。
> **权威来源**：`docs/02-implementation-plan.md`（各阶段交付物、退出标准、"可停点"表）、`docs/01-product-design.md` §7/§8、`docs/reference/decisions.md`（D8 / D9 / D10 / D11 / D19 / D24 / D25 / D31 / D45）。

## 0. 结论

- **阶段 1 的目标不是美观或易用**。退出标准全部是语义的（逐 hunk 裁决后逐字节符合预期、Accept 后 `Ctrl+Z` 不影响文档、Reject 后可撤销、文件级新建/删除、缺 Bun 明确报错），**零审美指标**；计划只约束 UI 的**形态**（D11 三处同步到同一次 `provideCodeLenses`、D24 的 Changes 列表规格、§7 的入口位置）。
- **UI 工作分三层，落在三个不同时点**：L1 从阶段 2 起每阶段收尾顺手做；**L2 的唯一锚点是阶段 5 收尾之后、阶段 8 之前**；L3 在阶段 8。

## 1. 三层与时点

| 层 | 内容 | 时点 |
| --- | --- | --- |
| **L1 可用性下限** | 新界面有命令入口与空态；状态文案不误导；新增字符串集中一处（为本地化铺路） | 阶段 2 起，**每阶段收尾** |
| **L2 视觉/交互打磨（锚点）** | 信息架构、状态词汇一致性、行形态、键盘流、无障碍、大 diff 密度 | **阶段 5 收尾之后** |
| **L3 分发级** | 本地化、高对比主题、首次运行引导、文档与录屏 | 阶段 8 |

## 2. 为什么锚点是"阶段 5 收尾"

评审面"要显示什么"在阶段 2–5 期间会被改写两次、扩容两次：

| 阶段 | 往 UI 上加什么 | 对已有界面的冲击 |
| --- | --- | --- |
| 2 台账 / 持久化 / 历史 | 回看第 N 轮、重新裁决、只读对话副本（D15） | **重**：评审面目前只呈现"每路径最新一轮"，阶段 2 要能切轮次 ⇒ Changes 列表与 `‹ k/N ›` 的含义都要重定义 |
| 3 权限转接 / 能力矩阵 | 审批对话框、"无前置闸门"声明、降级 UI、首次运行引导 | 中（新增 chrome）；**这部分是内容义务，不是打磨** |
| 4 会话生命周期 | 面板底部状态条（占用百分比 + 一键压缩，D31）、回退 / fork / steer 入口（D25） | 中：会话面板要从"消息流 + 输入框"变成 §8 的"消息流 + turn 列表 + activity" ⇒ 布局重排 |
| 5 反馈回路 | `rejected(user)` / `rejected(conflict)` / **"保留但内容是用户的"** 三种结局的呈现（D45 / D19），并按 hunk 给出区域、agent 当初写的文本、当前文本 | **重**：hunk 行标签、悬停浮窗、面板回执必须共用一套词汇 |
| 6 / 7 能力层 | `ide.*` 的 `fallback` 指示（D10） | 低（附加，不动骨架） |
| 8 泛化 / 分发 | 本地化、主题健壮性、首次运行、安装与文档 | 全局 |

阶段 2 与阶段 5 是**语义变更**（轮次维度、结局词汇），阶段 3 与阶段 4 是**布局变更**。审美工作只有在"要显示什么"稳定后才不会返工，而 2+3+4+5 恰好把这四件事补齐；此后 6/7 只加能力指示、8 才是分发。计划自身的"可停点"表指向同一处：阶段 3 = "可以每天自用"，阶段 5 = 闭环完整。

## 3. 为什么不更早、不更晚

- **更早（阶段 1/2 就做）**：形态已经锁死（D11 / D24 + 产品设计 §7），审美不在任何验收标准里 ⇒ 现在做**无法验收**，且会被阶段 2/3/4/5 推翻。D24 已经记下自维护 UI 的代价（主题、无障碍、本地化），那笔开销应当花在收敛后的界面上。
- **更晚（推到阶段 8）**：从阶段 3 起这套东西是**每天自用**的。若信息架构说不清状态，后续每个阶段的试用反馈都会被"看不出是功能不对还是界面没说清"污染。这是把锚点放在 5 而不是 8 的唯一理由。

## 4. 强制项（属于正确性，不能延后，也不算 L2）

- **D8 / D9 / D42**：未归因的改动**不得**呈现为已审阅；能力未声明时必须有降级显示；`permission.request: false` 时 UI 必须明示"无前置闸门"。计划已把"能力声明的完整落地与降级 UI"列为阶段 3 交付物。
- **D19**：被冲突丢弃的 hunk 必须可见，且与"用户拒绝"可区分。
- **D45**：三种结局的词汇（用户拒绝 / 冲突丢弃 / 保留但内容是用户的）在阶段 5 定型。

## 5. 提前触发的条件

命中任一条，就把 L2 提到**阶段 3 之后**：

1. 判断某个 hunk 的状态要靠猜（分不清 `pending` / `accepted` / `rejected(conflict)`）；
2. 一次真实任务里 hunk 数上到几十条时，Changes 列表或 inset 数量让人看不懂或卡顿（计划风险表里"insets 数量开销未知"正好一起解）；
3. 有第二个人（非作者）试用；
4. 阶段 2 的轮次切换与阶段 4 的状态条挤进同一面板后明显拥挤。

## 6. 每阶段的具体动作

- **阶段 2–5 收尾三条 L1 检查**：新界面有命令入口与空态；状态文案不误导；新增字符串集中一处。
- **阶段 3 顺手立规范**：`docs/reference/ui-conventions.md` —— 状态词汇表（D45 三种结局 + D19 的 conflict）、颜色只用 `--vscode-*` 变量、行高 / 间距 / 图标语义、键盘映射。**先立规范、阶段 5 后统一执行**，避免出现第二套并行约定。
- **阶段 5 之后那一轮（L2）**：信息架构；键盘流（下一个 / 上一个 hunk、Accept / Reject 快捷键）；无障碍（`aria-label`、焦点顺序、对比度）；大 diff 密度策略；空 / 加载 / 错误态。
- **阶段 8（L3）**：本地化、高对比主题、首次运行与文档。
