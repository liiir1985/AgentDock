# AgentDock Core 设计

> v1 · 2026-09-18。**产品行为**见 `01-product-design.md` §6；**决策裁定**见 `reference/decisions.md`（D1–D45）；**实现步骤**见 `02-implementation-plan.md`。
> 本文只讲设计——Core 的模型、语义与不变量，不含实现。与决策台账冲突时以后者为准。

## 1. 定位

Core 是宿主无关的**变更模型与裁决算法**：纯计算，不渲染、不写盘、不认 harness 协议、不碰 IDE API。

| | |
| --- | --- |
| **拥有** | 会话 / 轮次 / 变更集的记录结构；归因结果、快照与可还原性；diff 与 hunk 推导；reconcile；Accept / Reject 的**计划**；回退的文件侧；adapter 能力声明 |
| **不拥有** | 渲染与落盘（宿主）、会话侧回退 / fork / 压缩（harness）、权限的最终裁决（harness） |

同一份 Core 服务多个宿主：一期是 VS Code 扩展，之后 headless / CLI 复用。

## 2. 层级模型

`Session → Turn → ChangeSet → FileChange → Hunk`

| 层 | 语义 |
| --- | --- |
| Turn | 从用户 prompt 到 agent 完全完成；未产生变更的轮次允许没有 ChangeSet |
| ChangeSet | 该轮**可归因**的修改意图集合，不是磁盘快照 |
| FileChange | 一个文件的净形态：新建 / 修改 / 删除 / **真 rename**；附该轮开始前的文本 |
| Hunk | 一个评审单元：旧侧文本、旧侧来源、新侧在当前文本中的位置 |

### 2.1 坐标与字节

- 行级、0 基、闭区间；`end < start` 表示**位于该行的空区间**——纯插入与纯删除都用它表达。
- 旧侧**逐字携带行终止符**（含"末行无终止符"）。Reject 复原的是**字节**而非文本行，因此"只改了行尾"也是一次真实变更。
- 新侧坐标相对**当前文本**，旧侧内容相对**本轮开始前**。两者不是同一坐标系，任何编辑都会让新侧坐标失效——reconcile 存在的理由。
- 旧侧挂在哪一行（anchor）由 Core 给出，宿主不自算（D11）。

### 2.2 状态机

`pending → accepted | rejected(user | conflict)`

- **没有 `stale`**（D19）。无法定位的 hunk 只有两个归宿：并入一个更大的评审单元，或丢弃并标记 `rejected(conflict)`。
- `rejected(conflict)` 是**终态且不写盘**：它的文本已不在文档里，回写会毁掉外部内容；又必须**可见**（D19），故保留为零宽标记并继续跟随文档。
- `rejected(user)` 与 `rejected(conflict)` 语义不同，反馈回路依赖这一区分。

**"保留，但内容是你的"不是第四个状态**，而是 `accepted` + "用户改过 new 侧"（D45）。它有两种读法，取决于裁决是否已发生：

| | 含义 |
| --- | --- |
| `pending` + 用户改过 | 尚未裁决；**Reject 会把 old 覆盖上去**，连用户那几行一起丢弃（D3.2）——所以必须在动作前提示用户 |
| `accepted` + 用户改过 | 裁决保留的是**用户的文本**，不是 agent 写的 |

第二种是**唯一必须回传给 agent 的终态**（D3.3）：agent 要知道上一轮哪些改动被人改写。因此这个组合由模型显式命名（`hunkKeepsUserText`），而不是留给宿主去记一个布尔量——**文件级 / Accept All 必须逐 hunk 分流并汇总**，否则一次 Accept All 就把这件事抹平了。

这个标记精确到模型能知道的程度："一次非 agent 的编辑落在 new 侧内"。至于那些字节是否还在，由"该区域当前文本 vs agent 当初写的文本"比对回答——反馈载荷正是这么做。

### 2.3 身份稳定

- 平移与伸缩**保持身份**（就地更新区间，不重编号）；只有净形态变化（新建 / 删除 / 复原）才重建并重新编号。
- 合并会把已裁决的 hunk **重开**为待审：agent 重写了那段文本，旧裁决描述的是已经不存在的文本。

### 2.4 基线

- **懒快照**：首次触碰某路径时记录当时的文本；同一轮内第二次写入**不得**把基线挪到写后；轮次边界清空。与 Git 零耦合（D5）。
- **破坏性操作（删除 / 移动）在没有旧侧之前不许进入变更集**（D26）：拿不到基线就不记录，而不是记一条无法还原的账。

## 3. 归因

| 层 | 来源 | 要求 |
| --- | --- | --- |
| T1 | harness 内置文件变更工具 | **完全准确**：声明集合与包裹集合必须**相等**，少包一个即失败（D42） |
| T2 | shell | best effort：执行前解析命令意图（目标路径 + 可靠性） |
| T3 | 脚本 / 程序产物 | **不归因** |

- T2 的立场是**宁可漏不可错**：拿不准就整条跳过。错误归因会让 Reject 复原不属于 agent 的改动，比漏掉危险得多。
- **方言由 adapter 运行期提供，绝不从命令文本猜**（D43）；设备名（`nul` / `/dev/null` 等）不是路径；只写设备不产生变更。
- `write.intercept`（`own` / `blocking-hook` / `async-signal` / `post-hoc` / `none`）是**唯一**描述"我们多早、多确定地知道这次写入"的字段；判定只看写入前是否阻塞。

## 4. 可还原性

- 可还原性**不逐 hunk 记录**，由归因级别推导快照策略：写入前阻塞（`own` / `blocking-hook`）＝精确；`async-signal` ＝抢拍且有竞态；`post-hoc` ＝只有声明；`none` ＝不可审阅。
- 宿主必须按级别**如实呈现**，不能让用户以为到处都是逐字节可靠。
- 能力声明只强制两条互斥关系（其余如实声明即可）：MCP 注入仅存在于 MCP 通道；不可拦截写通道的 harness 不得声称能给出归因。

## 5. Reconcile

**问题**：hunk 的新侧坐标会被任何编辑作废。**目标**：任意编辑序列之后，裁决仍作用在正确的文本上。

### 5.1 编辑的来源决定语义

| 来源 | 语义 | 理由 |
| --- | --- | --- |
| agent 自己的编辑 | 必须**全部落进某个 hunk** | 否则这些基线行不再可达，Reject 无法逐字节复原 |
| 用户 / 外部编辑 | hunk 之外的文本**必须留在 hunk 之外** | Reject 只恢复各 hunk 自己的区域（D3），认领用户的文本等于删掉没人要求删的东西 |

来源带来的差异只有三处：agent 在无人覆盖的位置**新建评审单元**；跨边界时 agent **合并**、用户**重新定位**；合并会重开已裁决的 hunk。

### 5.2 单个 hunk 的归属

按序判断，首个命中即结论：

1. 编辑整体在其上方 ⇒ **平移**（按编辑的净行数）；
2. 编辑整体在其下方 ⇒ **不动**；
3. 编辑落在新侧之内 ⇒ 新侧区间**随之伸缩**，来源为用户时记 `userEdited`；
4. 跨边界 ⇒ **重新定位**：用 hunk 自身周围的上下文在编辑后的文本里找回它，命中必须**唯一**（两个可能的位置意味着我们不知道它在哪，猜错会把文本写回错误的地方）；命中失败按 5.1 分流。

### 5.3 三条不变量

- **一行只有一个主人**：hunk 有序且互不重叠。Reject 逐区域回写，重叠即互相覆盖，逐字节保证立刻失效。
- **一个位置只有一次归属**：同一位置恰好一个 hunk 认领纯插入（有行的那个优先，多个零宽 hunk 共位时取脚本序最后一个）；重定位若会落到兄弟 hunk 上，按"没找到"处理。
- **丢弃即标记**：被丢弃的 hunk 不再认领任何行，只留零宽标记，并继续随文档平移。

### 5.4 恢复范围

- 一个评审单元的旧侧 = 它能证明属于自己的基线范围（含它吞并的相邻改动；它新插入的行没有旧侧）。
- **Reject 是逐区域的**：只把各 pending hunk 的新侧区域写回旧侧文本；hunk 之外的文本（含用户自己写的行）保留。文件级 / 轮次级 Reject 是逐 hunk 的汇总，不是整文件回写。

## 6. 裁决

| 动作 | 写盘 | 语义 |
| --- | --- | --- |
| Accept（hunk / 文件 / 轮） | **否** | 只把 `pending` 标成 `accepted`；文档已经是 agent 改后的状态 |
| Reject（hunk / 文件 / 轮） | 是 | 生成"逐区域写回"的计划，由宿主执行 |

- Accept 逐 hunk 判断，因此它同时产出**两种保留**：干净的是 `accepted`，被用户改过的是 `accepted` + 用户改过（§2.2）。文件级与 Accept All 必须把两者分开呈现与汇总（D45）。
- 计划**先文件级操作、后逐区域回写**；同一文件的回写**从后往前**排列——调用方按返回顺序顺序应用，坐标始终有效，无需重算。
- 新建文件的 Reject ＝ 删除该文件；删除文件的 Reject ＝ 用基线重建；重命名的 Reject ＝ 先反向移动，再按旧路径回写。
- 已 `accepted` 的 hunk 不进 Reject 计划（Accept 从未改文档，包括保留用户文本的那种）；`rejected(conflict)` 永不进计划。回滚整轮是回退执行器的职责——**代价是它会盖掉"按你的文本保留"的区域**，所以含此类 hunk 的轮次在回退前必须警告。

## 7. 回退执行器

- 只做**文件侧**：给定轮次 N，产出"从当前状态回到第 N 轮开始前"的操作序列；会话侧回退 / fork 归 harness（D33）。
- 顺序就是算法的全部：**轮次倒序** + **轮内按首次触碰的逆序**，同一路径不合并——创建后再删除、重命名后再改内容这类序列只有顺序能保证正确。
- 纯计算、零 I/O：调用方写盘。

## 8. 确定性

同一脚本重放两次，台账必须逐字相同：无时钟、无随机标识，hunk 编号只由推导顺序决定。这是"重开也能复现当初裁决"的前提（阶段 2 的持久化依赖它）。

## 9. 验收（可测行为）

- 任意基线 + 任意 agent 写序列 ⇒ reject(all) 后文本**逐字节**等于基线。
- 用户编辑落在 hunk 内 ⇒ 同上逐字节；落在 hunk 外 ⇒ 用户的行留下，hunk 只平移。
- 用户改过 new 侧后：pending 时 Reject 会丢弃他的文本；Accept 后那份文本被保留且**可被识别出来**（`hunkKeepsUserText`），供下一轮回传 agent。
- 同一编辑序列重放两次，ChangeSet 完全一致。
- `revertTo(N)` 后，涉及文件逐字节等于第 N 轮开始前的状态。
- 跨边界编辑不产生 `stale`：能重定位就重定位，否则 `rejected(conflict)`。
- 构建产物出现对 IDE API 的依赖即失败；T1 的包裹集合 ≠ 声明集合即失败；三方言标注集逐条通过（可靠 = 路径正确，不可靠 = 整条跳过）。

## 10. 明确不做

- 不渲染、不写盘、不监控磁盘（D8）。
- 不从内容相似度**推断** rename：旧路径只来自 adapter 或命令解析器。
- 不解释脚本 / 程序产物（T3），不假装能审阅未归因的改动。
- 不做跨文件合并：每个文件各自一段评审单元序列。
- **不追踪裁决之后的后续敲键**：终态只记录"裁决发生在被改写过的 new 侧上"（D3.4：pending / accepted 不做特殊记忆）。用户在此之后又写了什么，由该区域的当前文本回答，也会成为下一轮 hunk 的基准。
